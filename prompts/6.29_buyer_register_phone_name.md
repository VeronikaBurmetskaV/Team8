# Реєстрація покупця: email або телефон, необов'язкове ім'я, «Підтвердити пароль»

Нові поля реєстрації покупця. Код: frontend/src/features/buyer-auth (BuyerRegisterPage.tsx, CSS Modules, api), shared/messages.uk.ts; бекенд — пакет ua.fulla.buyer (BuyerAuthController, сервіс, репозиторій), Flyway-міграції. Контекст: CLAUDE.md, docs/architecture/api.md §2.3, data-model.md, ADR-0012, ADR-0004 (JdbcClient, без JPA), react-hook-form + zod.

1. Форма /register:
   - «Ім'я» — необов'язкове, 1–50 символів після trim, перше поле; підпис «Ім'я (необов'язково)»; autocomplete="given-name".
   - Замість «Email» — одне поле «Email або номер телефону» (autocomplete="username", inputMode="email"):
     • якщо є «@» — це email (як зараз);
     • інакше — телефон: дозволені цифри, пробіли, дужки, дефіси, «+»; нормалізація в E.164; українські формати 0XXXXXXXXX, 380XXXXXXXXX, +380XXXXXXXXX → +380XXXXXXXXX; інші країни — лише з «+» і 8–15 цифр; інакше помилка «Введіть email або номер телефону у форматі +380…».
     • логіку визначення й нормалізації винеси в чисту функцію parseLoginId(value) → { kind: 'email' | 'phone', value } | null у спільний файл (знадобиться і для входу), з тестами.
   - «Повторіть пароль» перейменуй на «Підтвердити пароль» (і в повідомленнях помилок).
   - Текст під кнопкою «Ми зберігаємо лише ваш email і список вподобаних товарів» онови: «Ми зберігаємо лише ваш email або телефон, ім'я (якщо вкажете) і список вподобаних товарів».

2. Бекенд:
   - Flyway-міграція для buyer_accounts: email стає необов'язковим; нова колонка phone varchar(16) (E.164, CHECK формату '^\+[1-9][0-9]{7,14}$', UNIQUE); нова колонка display_name varchar(50) NULL; CHECK, що заповнено рівно одне з email/phone або хоча б одне (обери й поясни; рекомендовано — хоча б одне). Наявні акаунти не ламаються.
   - POST /api/buyer/register приймає { login, password, name? } (або { email?, phone?, password, name? } — обери за стилем api.md і поясни); сервер сам нормалізує і перевіряє телефон тими ж правилами, що фронтенд; email — як зараз.
   - помилки: зайнятий email або телефон — та сама нейтральна відповідь, що зараз для email (не розкривати, що саме зайнято); неправильний формат — відповідний код; ім'я довше 50 — VALIDATION_FAILED з fields.name.
   - сесія після реєстрації — як зараз.
   - телефон НЕ перевіряється SMS — зазнач це в ADR.

3. Документація: api.md (тіло register, помилки), data-model.md (колонки), коротке доповнення до ADR-0012 або новий ADR: вхід по email або телефону, ім'я необов'язкове, телефон без підтвердження (наслідки: немає відновлення пароля через телефон, можна вказати чужий номер).

4. Тести: parseLoginId (email, 0XX…, 380…, +380…, з пробілами/дужками, іноземний +, сміття); бекенд — реєстрація з email, з телефоном, з ім'ям і без, дубль телефону, неправильний телефон, довге ім'я; фронтенд — «Підтвердити пароль» і помилка, якщо паролі не збігаються; ім'я необов'язкове.
