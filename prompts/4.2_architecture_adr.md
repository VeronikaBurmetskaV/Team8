## 2 Step 1: the plan

First the plan — don't choose anything yet. Which technical decisions must be made before the code starts, in which order (what depends on what), and which options exist for each:

0. application architecture style (layered/MVC, clean/hexagonal, modular monolith, microservices — and separately for the frontend);
1. platform: web or mobile (React or React Native) — based on the buyer journey (the buyer opens the site from a phone and swipes cards) and the brand journey (the brand fills in product cards in a cabinet);
2. repository structure (mono/polyrepo, how to split the code);
3. frontend: build, routing, working with server data, styles, swipe gestures, storing «Вподобане» on the client (US-09, US-16);
4. backend: framework, validation, error format, API style;
5. data store and ORM, with local launch and free hosting in mind;
6. authentication — taking into account the gaps from the digest: buyers have no account, brands register with email + password (US-21) but there is no brand login story;
7. storing uploaded images (brand logos US-22.1, product photos US-25.1) with a 0 UAH budget;
8. consistency and concurrency: unique brand email on simultaneous registration (US-21), no duplicates in «Вподобане» on double click (US-09, US-10), what the buyer sees when a brand publishes or unpublishes a card mid-session (US-31), checking the brand product link (US-26);
9. deployment and hosting.

If you lack information for the rating — ask me before writing the plan.

## 3 Step 2: documents

After I approve the plan, write, in this order:

### 3.1 `docs/analysis/options.md`

For each decision, a table of options rated against OUR constraints (+ / 0 / −), the main criterion that tips the choice, and what would have to change for the choice to be different.

At the end — a summary table: decision → what it leans toward → main criterion → ADR number.

### 3.2 `docs/adr/NNNN-short-name.md`

One file per decision, fixing the choice: 2–3 options from `options.md` with trade-offs specifically for this team, a recommendation and consequences (what becomes simpler, what becomes harder, what we postpone). If you disagree with what `options.md` leans toward — say why.

Format:

```
# ADR-NNNN: Title
Status | Context | Options (with pros/cons) | Decision | Consequences | Related stories.
```

Add `docs/adr/README.md` with an index and a rule for when an ADR should be written and when not. Write concisely: ADRs are read, not studied.

### 3.3 `docs/architecture/risks.md`

A risk register in three groups: **technical**, **product** (requirements/user behavior), **team** (deadlines, skills). For each: probability and impact (low/med/high), trigger (how we will notice that the risk has fired), mitigation, and where exactly it lives (component / ADR). No generic phrases like «bugs are possible». Separately mark the risks we consciously accept for the MVP.

### 3.4 `docs/architecture/integrations.md`

All external dependencies (brand websites that product links lead to, image storage, hosting, DB): what exactly we take from them, whether it is an API integration or just a link/format, what we do if the dependency is unavailable (e.g. the brand site is down or the product page returns 404 — US-19, US-26).

Automatic import from brand sites (US-23, US-24, US-27–US-30) is **Out of Scope** — mention it only as a future integration.
