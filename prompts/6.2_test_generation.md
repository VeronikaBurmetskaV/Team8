
# Промпт: Автотести за критеріями приймання (US-25.1, US-31, US-10) + перевірка «зламай код»

Напиши автотести для трьох ключових історій FULLA прямо за їхніми критеріями приймання
(Gherkin S1/S2 і чек-лист CL) і доведи, що тести справжні: тимчасово зламай код і переконайся,
що вони червоніють. Суворо дотримуйся CLAUDE.md (§4.2, §5, §6.14, §7) і `docs/testing-strategy.md`.

Тільки тести. Код програми (`backend/src/main/**`, `frontend/src/**` крім `*.test.ts(x)`)
змінюється **лише тимчасово** на кроці 4 і повертається назад. Нових залежностей не додавай.
Наявні тести не змінюй, не вимикай і не послаблюй.

## 1. Карта «сценарій → тест»

Спершу для кожної з трьох історій склади таблицю: кожен пункт S1, S2 і CL → наявний тест
(клас.метод або файл › назва) або «немає». Нові тести пиши **лише для прогалин** і для пунктів,
де наявний тест перевіряє не все, що каже сценарій. Не копіюй наявні тести під новою назвою.

## 2. Тести

Кожен тест прив'язаний до сценарію: у назві або в коментарі над ним — ID історії і сценарію
(`US-31 S2`, `US-25.1 CL`). Перевіряй те, що бачить користувач або клієнт API: HTTP-статус, код
помилки з конверта, стан у БД через API, список карток, стрічку. Не перевіряй деталі реалізації.

### US-25.1 + US-26 — створення чернетки картки (бекенд, MockMvc + embedded Postgres)
- S1: бренд з активним профілем (назва збережена, згоди немає) створює «Лляна сукня міді», 2400 грн,
  https-фото, посилання → `201`, `status: "DRAFT"`, `brandName` з профілю, картки **немає** в `GET /api/feed`.
- S2: ціна `-500`, `0`, текст (`null` / рядок), відсутнє фото → `400 CARD_INVALID_PRICE_OR_PHOTO`,
  у `fields` правильне поле, картка не з'явилась у `GET /api/brand/products`.
- US-26 S2: посилання без `http(s)://` → `400 CARD_INVALID_URL`.
- CL: бренд без збереженої назви → `409 PROFILE_INCOMPLETE`.
- Фронтенд (Vitest): схема форми з `shared/validation.ts` / `cardForm.ts` відхиляє ті самі значення ціни,
  і помилку показують дослівним текстом із `messages.uk.ts` («Вкажіть коректну ціну більше нуля…»).

### US-31 + US-22.2 — публікація (бекенд + фронтенд)
- S1: бренд зі згодою публікує чернетку → `200`, `PUBLISHED`, `publishedAt` не `null`, картка є в `GET /api/feed`.
- S2: бренд без згоди → `409 CONSENT_REQUIRED`, картка лишається `DRAFT`, у стрічці її немає.
- Edge: повторна публікація → `409 INVALID_STATE`; чужа картка → `404 NOT_FOUND` (не 403);
  покупець → `403`; без CSRF → `403`.
- Фронтенд: на `/brand/products` без згоди кнопка «Опублікувати у стрічку» `disabled` і є текст
  `CONSENT_REQUIRED` з посиланням на `/brand/profile`; зі згодою кнопка активна.

### US-10 + US-09 — пропуск і лайк у стрічці (фронтенд, Vitest)
- US-10 S1: skip картки №5 → «Вподобане» не змінилось, поточна — №6.
- US-10 S2: два skip для №5 поспіль → пропущено лише №5, показується №6 (не №7).
- US-10 CL: пропущена картка не повертається в чергу після повторного завантаження стрічки.
- US-09 S1: like → картка в `favoriteIds`, показується наступна; повторний like тієї самої — без дубля.

### Файли
- Бекенд: нові класи поруч із наявними — `backend/src/test/java/ua/fulla/products/CreateCardAcceptanceTest.java`,
  `PublishAcceptanceTest.java`; ізоляція — `@AutoConfigureEmbeddedDatabase(provider = ZONKY)` і унікальні
  email через `UUID.randomUUID()`, як у `docs/testing-strategy.md` §3. Без `DELETE`/`TRUNCATE`.
- Фронтенд: `frontend/src/features/feed/queue.acceptance.test.ts`,
  `frontend/src/features/cabinet-products/cardForm.acceptance.test.ts` (за потреби — сторінка публікації).

## 3. Запуск однією командою

Усі тести (фронтенд + бекенд) мають проходити командою з кореня:

```bash
npm test
```

Додатково перед завершенням: `npm --workspace frontend run lint` і `npm --workspace frontend run typecheck`.

## 4. Перевірка «зламай код навмисно»

Для кожної поломки: внеси її → запусти **лише** потрібні тести → переконайся, що вони червоні →
`git checkout -- <файл>` → переконайся, що знову зелені. Ламай по одній, ніколи дві разом.

| № | Файл | Поломка | Має почервоніти |
|---|---|---|---|
| 1 | `backend/.../products/ProductRepository.java` | у SQL публікації прибрати умову `EXISTS (… consent_given_at IS NOT NULL)` | US-31 S2 |
| 2 | той самий | у SQL публікації прибрати `AND status = 'draft'` | повторна публікація → `INVALID_STATE` |
| 3 | запис-запит створення картки (`products/…Request.java`) | послабити правило ціни (`@Positive` → `@PositiveOrZero` або прибрати) | US-25.1 S2 (ціна 0 / -500) |
| 4 | `frontend/src/features/feed/queue.ts` | у `feedReducer` прибрати `if (state.viewedIds.includes(action.id)) return state;` | US-10 S2 |
| 5 | той самий | у гілці `skip` додавати ID ще й у `favoriteIds` | US-10 S1 |
| 6 | `frontend/src/features/cabinet-products/publishGate.ts` | замінити `!== "CONSENTED"` на `=== "CONSENTED"` | US-31 S2 (фронтенд) |

Команди для швидкого запуску окремих тестів:
`cd backend && ./mvnw test -Dtest=PublishAcceptanceTest`,
`npm --workspace frontend run test -- queue`.

Якщо після поломки тест лишився **зеленим** — він фейковий: виправ тест (не код), повтори.
Після всіх поломок `git status` / `git diff` для `src/main` і не-тестових файлів фронтенду — порожні.
