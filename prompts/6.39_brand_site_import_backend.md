# Імпорт товарів з сайту бренду в його кабінет (бекенд)

Імпорт товарів з сайту бренду в його кабінет (бекенд). Контекст: CLAUDE.md, docs/architecture/integrations.md (правило A-15: сервер не звертається до сайтів брендів), ADR-0014 (демо-імпорт: PoliteFetcher, CatalogSyncService, VsiSvoiFeedImporter, парсери sitemap + JSON-LD, ліміти, відкладена перевірка SSRF), ADR-0004 (JdbcClient, без JPA), Flyway, api.md, data-model.md, domain-model.md (згода, публікація). Спершу прочитай усе це.

0. Рішення: напиши новий ADR (наступний номер) «Імпорт товарів з сайту бренду за його запитом»: чому змінюємо A-15 (бренд сам ініціює імпорт свого сайту і дав згоду), обмеження, безпека, що лишається забороненим (жодних запитів за посиланнями без підтвердженого власника; демо-імпорт ADR-0014 лишається лише dev). Онови integrations.md (A-15 з винятком і посиланням на ADR).

1. Підтвердження власності сайту (обов'язково до імпорту):
   - для профілю бренду генерується токен; бренд підтверджує сайт ОДНИМ зі способів: (а) мета-тег <meta name="fulla-verification" content="<токен>"> на головній сторінці; (б) файл https://<домен>/fulla-verification.txt з токеном; (в) автоматично, якщо домен email бренду збігається з доменом сайту (лише для доменів не з публічних поштових сервісів: gmail, ukr.net, i.ua тощо — список у конфігурації);
   - ендпоінт POST /api/brand/site/verify — перевіряє, зберігає verified_at і домен; зміна websiteUrl на інший домен скидає підтвердження;
   - Flyway: колонки verification_token, site_verified_at, site_domain.

2. Безпека запитів (SSRF) — спільний захищений fetcher для всіх запитів на сайти брендів:
   - лише https, порт 443; DNS-резолв і відмова для приватних/спеціальних адрес (127/8, 10/8, 172.16/12, 192.168/16, 169.254/16, ::1, fc00::/7, link-local, multicast тощо) — і перевірка повторюється після кожного редиректу (максимум 3 редиректи, лише на той самий зареєстрований домен або його піддомени);
   - тайм-аути, ліміт розміру відповіді, дозволені content-type, власний User-Agent «FULLA-bot (+посилання на сторінку про бота)», повага до robots.txt, пауза між запитами (як PoliteFetcher), ліміт запитів на один імпорт;
   - перевикористай і доповни PoliteFetcher, не дублюй.

3. Пошук товарів на сайті (у такому порядку, перший, що спрацював):
   - товарний фід, якщо бренд вказав його URL (окреме необов'язкове поле feedUrl у профілі; той самий домен) — формат Google/Facebook (як VsiSvoiFeedImporter);
   - Shopify: /products.json (якщо сайт на Shopify);
   - sitemap.xml (+ sitemap index) → сторінки товарів → JSON-LD Product (як парсери One By One / Cher'17, але узагальнено).
   - Узагальни наявні парсери з ADR-0014 в один «generic» імпортер; специфічні під конкретні сайти не додавати.
   - фільтр лише одягу (як зараз), ліміт товарів на один імпорт (наприклад 50, у конфігурації).

4. Збереження:
   - імпортовані товари належать бренду (brand_id), створюються як ЧЕРНЕТКИ (не опубліковані), з полем джерела (source_url, external_id) щоб повторний імпорт оновлював, а не дублював;
   - зберігаються: назва, ціна, фото (лише URL або через наявний механізм зображень — як у товарах бренду), посилання на товар, розміри з наявністю, колір, матеріал, опис;
   - повторний імпорт: оновлює ціну/розміри/наявність; товари, яких більше немає на сайті, приховуються (як у CatalogSyncService, лише після повного успішного прогону); вручну відредаговані брендом поля не перезаписуються (позначка «змінено вручну»).

5. API (онови api.md):
   - POST /api/brand/site/verify, POST /api/brand/import (запускає імпорт асинхронно; не частіше ніж раз на 10 хв для бренду), GET /api/brand/import/status (стан: idle/running/done/failed, скільки знайдено/додано/оновлено/пропущено, помилки зрозумілими кодами, час останнього імпорту);
   - помилки: SITE_NOT_VERIFIED, NO_PRODUCTS_FOUND, SITE_UNREACHABLE, IMPORT_TOO_FREQUENT тощо — у таблицю помилок.
   - автоматичне оновлення раз на добу для брендів з підтвердженим сайтом і хоча б одним імпортованим товаром (той самий механізм розкладу, що в ADR-0014, але в усіх профілях, не лише dev).

6. Публікація: імпортовані чернетки публікуються тим самим механізмом, що й звичайні товари бренду (окремий товар і масово — POST /api/brand/products/publish з масивом id, якщо такого ще немає); правило згоди з domain-model.md діє як для звичайних товарів.

7. Тести: SSRF (приватні IP, редирект на приватну адресу, http://, інший домен); підтвердження мета-тегом, файлом, доменом email, публічна пошта не підтверджує; імпорт з фіду, Shopify JSON і JSON-LD (локальні фікстури, без реальних сайтів); повторний імпорт оновлює без дублів; ручні зміни не перезаписуються; ліміт частоти.

Збережи цей промпт у prompts/ з наступним номером.
Наприкінці: cd backend && ./mvnw verify. Коротко опиши змінені файли і що лишилось для фронтенду.
